# 测试用例编写准则（推荐）

本文件是测试编写的默认准则，优先级高于 `docs/agents/deps/tdd.md`：后者只提供红 → 绿机制与 seam 基线。是否测试由 agent 按变更风险自行决定（用户也可要求）；一旦发生任何测试行为，本文件全量生效。

## 0. 术语

- **必须 / 禁止**——硬性要求；违反即测试产出不合格。
- **应该 / 不应**——默认要求；偏离需在自检报告中说明理由。
- **可以**——可选。
- **SPEC ID**——SPEC 中可验收的行为、契约、边界或防御层级的稳定标识。
- **防御层级**——SPEC 指定承担输入校验、鉴权、限流、事务、幂等、超时重试等的专门防线。
- **变更等级**——L1 SPEC 变更｜L2 测试缺陷｜L3 结构重构（断言语义不变）｜L0 仅实现变更。
- **临时测试**——agent 为验证本次变更新写、不提交、收尾删除的测试。
- **落盘测试**——提交进仓库、长期提供回归保护的测试。

## 1. 三种测试行为

| 行为 | 目的 | 是否提交 | 需要的产出 | 追溯 |
| :--- | :--- | :--- | :--- | :--- |
| **执行** | 证明既有行为未被破坏 | 否 | 命令 + 结果 + 跳过 / 缺口 | 无 |
| **临时自验** | 开发期验证新行为 | 否 | 场景 + 强断言 + 结果；收尾删除 | 无 |
| **落盘** | 长期回归保护 | 是 | 计划 / 用例表 / 矩阵 / 自检（§4，按分级） | SPEC ID；无 SPEC 时降级到 issue 完成判据并标 `待回写 SPEC` |

- §6、§7 的有效性规则对三种行为一律适用。三者区分的是**文书负担**，不是标准。
- 临时测试不是验收证据：只能表述为「开发期自验（临时）」；Current 的信心可记 `tested (one-off)`，绝不构成回归覆盖。
- 临时测试写在项目声明的 scratch 路径（默认 `tmp/`，须 gitignore），收尾删除；绝不进入提交，也绝不留在正式测试目录里。
- **bug 修复**：默认落盘至少一条针对该缺陷的回归用例（走精简档即可）。判断不值得落盘时，允许只留临时证据，但必须在 `## 测试` 写明理由。项目声明无测试面时不适用。

## 2. 总则

- **SPEC 是唯一真源**（对落盘测试）。每个用例至少追溯一个 SPEC ID；无 SPEC 时追溯到 issue 完成判据并标 `待回写 SPEC`。禁止从实现反推期望。
- 落盘与临时测试都**先行或与实现同批提交**；禁止实现完成后补测试凑绿。
- **测可观察行为**——业务值、副作用、错误契约。禁止断言私有方法、内部调用次数 / 顺序，除非 SPEC 明确将其定义为契约。
- **上下文隔离。** 测试作者只拿 PRD 摘要、SPEC、公开签名、防御层级定义。实现可见时必须声明，交人工复核是否污染测试。
- **防御分层。** 防御逻辑只在所属层级测。找不到归属就提问并标 `防御归属缺失`，绝不自行发明场景。
- **变更受控。** 改落盘期望必须引用 SPEC 变更或测试缺陷；L0 绝不作为理由。

## 3. 输入

必须有：PRD 摘要（只提供业务命名与场景词汇，不作验收依据）、SPEC 条目、防御层级定义、公开签名、既有测试约定（目录、命名、框架、数据构造）、项目的测试入口命令、scratch 路径。

禁止：以「实现里现在是这样」为依据；补 SPEC 未定义的规则；用 Fixture / Mock 替被测代码完成业务步骤。

SPEC 歧义、冲突或缺失 → 输出待确认问题清单，绝不静默假设。

## 4. 产出

**每个 bug / feature / chore issue 都带 `## 测试` 节**——缺失即视为没交代（`suggestion` 不是工作条目，不设此节）。三个固定槽位：

```markdown
## 测试
- 执行：<命令> → 通过 ｜ 跳过 N（原因）
- 临时：<场景> → 通过，已清理 ｜ 无
- 落盘：<用例> ↔ <SPEC ID / 完成判据>（无）
```

在此之上：

1. **落盘——测试计划**（按 SPEC 条目）：层级、正 / 反 / 边界场景、Mock 理由、防御归属、未覆盖项、假设。
2. **落盘——用例表**：Case ID｜SPEC ID｜层级（单元 / 契约 / 集成 / E2E）｜业务语言描述的行为｜Given / When / Then｜数据与边界类型｜Mock 及理由｜防御层级｜变更等级。
3. **落盘——测试代码**：名称表达行为（`should_reject_order_when_stock_insufficient`）；失败信息含期望与实际业务值；名称与信息要能让非实现者读懂。
4. **落盘——追溯矩阵**：SPEC → Case，并列出未覆盖条目及原因。
5. **落盘——自检报告**：运行命令与结果、未覆盖项、实现可见性声明、疑似越权防御。

分级：feature 与结构性变更交付全部五件；bug 修复与 chore 精简为追溯一行 + 强断言 + 自检证据——追溯、断言强度、Mock 理由三项绝不省略。临时行为只需 `## 测试` 的一行；只跑既有测试只需「执行」行。

## 5. 用例设计（落盘）

- 一测一行为；参数化覆盖同一行为的多组数据。
- 按 SPEC 取舍覆盖：主流程；SPEC 业务异常与错误契约；输入边界（空、空白、超长、极值、Unicode / 特殊字符、非法格式）；状态转换、幂等、并发；防御层拦截。
- 不凑覆盖率：不要无断言用例、重复分支、只走通不校验。
- SPEC 定义的自由输入按脏数据参数化；未定义就提问，不自定规则。

## 6. 断言、Mock、Fixture（三种行为一律适用）

- **强断言**：业务值、状态、副作用、错误码 / 类型 / 契约消息。金额、时间、集合顺序按契约断言精度与顺序。
- 禁止：`assert result is not None`、仅校验类型、仅校验 truthy。错误路径断言具体契约，而不只是「抛了异常」。
- **Mock** 只隔离外部依赖、不确定源或 SPEC 要求隔离的协作者；契约取自 SPEC 或公开接口，每个都写明理由。禁止 mock 私有协作者；禁止验证调用次数 / 顺序，除非 SPEC 明确要求（如「幂等键只触发一次退款」）。
- **Fixture** 只准备前置状态，绝不插入业务副作用。让本应失败的流程变绿的 Fixture 属高风险，须人工复核。

## 7. 防御专项

每个防御用例标注层级与 SPEC ID；业务用例不重复测各层防御。SPEC 未映射的实现分支 → 标 `疑似越权防御`，不补测试使其合法化。测试绝不要求实现新增防御代码。

## 8. 变更管理（落盘）

- **L1**——SPEC 变更；可改语义与期望，须引用 SPEC 变更 ID。
- **L2**——测试缺陷；修正并说明。
- **L3**——重构 Fixture、Mock 组织、参数化方式；断言语义不变。
- **L0**——仅实现变更；绝不作为改期望的理由。

重构后测试失败，先判行为：未变 → 修结构；变了 → 回到 SPEC。

## 9. 交付门禁

- [ ] issue 的 `## 测试` 已填：执行证据、临时结论、落盘追溯（或在「无」处写明理由）
- [ ] 每个 SPEC 行为至少一条落盘用例，或已列出缺口
- [ ] 任何行为中都无实现细节断言（私有方法、调用次数）
- [ ] 关键断言强，失败信息可读
- [ ] 每个 Mock 有理由；无 Fixture 补全业务逻辑
- [ ] 防御用例标注层级；无疑似越权防御被新测试掩盖
- [ ] 临时测试已删除；`git status` 无 scratch 残留
- [ ] bug 修复：已落盘回归用例，或 `## 测试` 写明了不落盘的理由
- [ ] 测试可独立、可重复运行（不依赖真实网络、当前时间、执行顺序）
- [ ] 附运行命令与结果——只声称「测试通过」不算证据
- 关键模块建议执行变异测试；存活变异体需人工评审。

**人工评审看四件事**：用例源自 SPEC 而非代码；断言是否够强；Mock / Fixture 是否在替实现干活；防御是否留在本层。覆盖率只作诊断，不作质量结论。
